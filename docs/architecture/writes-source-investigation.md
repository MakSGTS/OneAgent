# Writes Source Investigation

## Status and purpose

This document is a focused, read-only investigation of repository-owned source
evidence for the first Writes slice accepted by
`docs/adr/0022-writes-semantics.md`. It defines the smallest source corpus that
can be created before Document register declaration extraction or a Writes
candidate parser is implemented. It does not redefine the accepted Writes
contract, change production behavior, or create fixture files.

Evidence labels have strict meanings throughout this document:

- **Confirmed** means that the current repository contains the cited source,
  implementation, test, or Coverage evidence.
- **Accepted** means that ADR-0022 requires the behavior, even when the current
  repository has no corresponding source example or implementation.
- **Unknown** means that repository-owned evidence is absent or insufficient.
  Unknown forms do not authorize syntax, classifications, or fixtures.

### Source inventory conclusions

The repository contains many genuine persistent operations outside the first
slice, including bare object `Write()`, record-set writes with arguments,
Document object writes, and collection-level `RegisterRecords.Write()`. It also
contains many non-persistent file and presentation writes. These occurrences
confirm why the method name alone cannot select a graph target.

The selected corpus is intentionally representative. Adding every textual
occurrence would add duplication without changing the accepted boundary and
would make provenance and expected outcomes harder to review.

## Accepted ADR-0022 requirements

The following requirements are **Accepted** even where implementation or a
negative source example does not yet exist:

1. The first source endpoint is an existing `NodeKind::Procedure` in the Object
   Module of a discovered EDT Document.
2. The complete standalone statement must have exactly
   `RegisterRecords.<RegisterName>.Write()` shape and zero arguments.
3. Comments, strings, assignments, additional expressions, aliases, localized
   spellings, chained receivers, dynamic receivers, and non-empty arguments are
   not accepted by the first slice.
4. The owning descriptor must supply exactly one compatible typed
   `AccumulationRegister.<RegisterName>` declaration.
5. Resolution must find exactly one existing top-level
   `Metadata(AccumulationRegister)` node. Missing, ambiguous, incompatible,
   partial, external, or dynamic targets do not create placeholders.
6. Candidate, declaration, diagnostic, resolution, and provenance ordering must
   be deterministic. Repeated statements for one Procedure-target pair support
   one edge with sorted and deduplicated provenance.
7. Parser and resolution failures are typed no-edge outcomes. One unsupported
   statement does not invalidate another independently complete accepted
   statement in the same Procedure.
8. The graph endpoint matrix, Query behavior, Impact behavior, identity, public
   APIs, and Coverage state remain unchanged during corpus creation.

These are fixture expectations only where the repository has confirmed source
evidence. An Accepted diagnostic requirement does not by itself authorize an
invented malformed or localized input file.

## Recommended fixture topology

### Decision

The corpus should be split by ownership boundary:

- lexical and complete-statement evidence belongs under the existing
  `crates/bsl/tests/fixtures` directory in a new `writes` subtree;
- the canonical positive ownership/declaration/resolution evidence belongs
  under the existing `adapters/edt/tests/fixtures` directory in one new static
  `writes_project` subtree;

  typed models exist.

module belongs to a Document, that the Document declares both register targets,

separate positive projects per target would duplicate all ownership evidence.

## Copying, reduction, and determinism rules

The next corpus-creation task must apply all of these rules:

1. Every copied source fragment must have one manifest entry containing the
   original repository path, inclusive original line range, fixture line range,
   source Git blob ID, normalized fragment SHA-256, and treatment: `verbatim`,
   `bounded-excerpt`, or `generated-scaffold`.
2. A verbatim line preserves all characters between its first and last
   non-line-ending bytes. Indentation may be changed only when the manifest
   labels a generated wrapper; the statement token sequence and spelling must
   remain unchanged.
3. Bounded excerpts must remain contiguous. If unrelated statements are
   removed, the replacement wrapper is generated scaffolding and must not be
   described as a verbatim excerpt.
4. The positive Procedure wrapper may be generated, but the two call statements
   must be copied exactly and kept in CashAccountBalance-then-RefundBankPayment
   order. No additional accepted-looking write is added.
5. Reduced XML descriptors preserve the real root metadata kind, UUID, exact
   `<name>`, and selected declaration text. Unrelated properties and children
   may be removed only when the current EDT loader accepts the reduced document.
6. The generated Configuration descriptor is structural scaffolding. Its UUID
   and name must be fixed constants recorded in the manifest and must not be
   presented as real-source evidence.
7. Fixture files use UTF-8 without BOM, LF line endings, and one terminal LF.
   The inspected positive XML sources already use UTF-8 without BOM and LF.
   The original Object Module uses LF but has a leading blank line and no
   terminal LF; the generated reduced wrapper deliberately follows repository
   fixture convention instead, with the source-to-fixture line map recording
   the difference.
8. Manifest tables and test enumeration use lexical filename order. Semantic
   expectations never depend on filesystem order. The positive candidate order
   is explicit source order `(fixture line, normalized register name)`.
9. Duplicate semantic cases are not copied into multiple fixtures. The static
   positive Object Module is shared by BSL and EDT tests. Later tests may copy it
   into temporary directories but must not maintain a second source-of-truth
   file.
10. Future modifications to a source-derived line require updating its manifest
    origin, treatment, expected outcome, and source-to-fixture mapping in the
    same change. Tests should assert the two exact positive spellings so that a
    fixture edit cannot silently broaden the accepted contract.
11. No fixture may be created from an Unknown case. When evidence becomes
    available, this investigation or a successor must first record the source
    and classification.
